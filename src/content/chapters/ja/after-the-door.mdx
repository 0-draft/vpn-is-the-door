<Summary lang="ja">
  <p>ランサムウェアの被害は、いくつもの手順が続いた結果である。VPN の扉から始まり、多くの場合は数日後の暗号化で終わる。画面が止まった時点で、侵入者はすでに社内の鍵を握り、バックアップを消し、データを外へ運び出している。</p>
  <p>ここから導かれる判断は、侵入者がすでに中にいる前提で備えることである。侵入者が届かないバックアップと、使い回せない管理者アカウントがあれば、扉が破られても被害は限られる。</p>
</Summary>

    <p>侵入者はこの扉から入った。漏れていたパスワードを使ったか、機器そのものの欠陥を突いたかのどちらかである。窓は割られていない。</p>

    <p>このページの後半で取り上げる二つの病院では、同じ管理者パスワードが複数のサーバで使い回され、何度失敗してもアカウントがロックされない設定だった。</p>
  </Step>
  <Step n={5} title="先にバックアップが消される">

  </Step>

## <Scale s="1:100" /> どの手順にも、情報システム担当が見られる痕跡が残る

上の手順はどれも見えないわけではない。VPN 機器、Active Directory、ファイルサーバ、バックアップソフトなど、たいていの会社がすでに持っているログに記録が残る。問題は、日曜日の午前3時にそのログを誰も見ていないことである。以下、手順ごとに、記録がどう見えるかと、侵入からどれくらいで現れるかをまとめる。各手順の枠には、ログを確認する人に見えたはずのものを挙げた。例は典型的なパターンで、港精密で起きた出来事ではない。

### 手順2：本人らしくないログイン

VPN 機器から見れば、正しいアカウントによる普通のログインである。おかしいのは状況だけだ。

<Signs lang="ja" step={2} time="侵入の時点">
  <ul>
    <li><span class="where">VPN のログ</span>本人が寝ているはずの午前3時に、国外やホスティング事業者のアドレスからログインが成功している。</li>
    <li><span class="where">VPN のログ</span>その直前にログイン失敗が続いている。パスワードが最初から分かっていれば、失敗は一度もない。</li>
    <li><span class="where">VPN のログ</span>もう存在しないはずのアカウントでログインしている。退職者や、契約の終わった業者のアカウントである。</li>
  </ul>
</Signs>

### 手順3：在宅勤務のはずの1人が数十台に触れる

侵入者は社内のアドレスを得て、ネットワークの地図を作り始める。入口のメール検査やウイルス対策には何も通っていないので、何も記録されない。

<Signs lang="ja" step={3} time="5分以内">
  <ul>
    <li><span class="where">ファイアウォール</span>1本の VPN セッションが、数分のうちに社内の数十のアドレスへ接続している。</li>
    <li><span class="where">サーバ</span>1台から多数のサーバへリモートデスクトップ接続が試みられている。大阪の病院の事例では、侵入者は約240の IP アドレスの情報を集め、1台のサーバから約70のアドレスへリモートデスクトップ接続を試みた。</li>
  </ul>
  <SourceLine lang="ja" ids={["arcticwolf-akira-2025", "osaka-report-2023"]} />
</Signs>

Arctic Wolf の観測では、SonicWall の VPN にログインした Akira の攻撃者は「5分以内」に社内ネットワークの探索を始めていた。

### 手順4：新しい管理者が現れる

侵入者は Active Directory の管理者アカウントを乗っ取るか、新しく作る。ここから先は、どの内扉も開く。

<Signs lang="ja" step={4} time="中央値3.40時間">
  <ul>
    <li><span class="where">AD</span>誰も申請していないユーザーアカウントができている。または既存のアカウントが Domain Admins グループに追加されている。</li>
    <li><span class="where">AD</span>管理者アカウントが VPN のアドレスからログオンしている。</li>
    <li><span class="where">サーバ</span>サーバのウイルス対策ソフトが削除されるか、止められている。大阪の事例でも、侵入者は最初に入った病院のサーバでウイルス対策ソフトをアンインストールした。</li>
  </ul>
  <SourceLine lang="ja" ids={["sophos-aar-2026", "osaka-report-2023"]} />
</Signs>

Sophos の2025年の事例データでは、侵入してから Active Directory への最初の試みまでの時間は中央値で3.40時間だった。2024年のデータでは11時間である。

### 手順5：バックアップのジョブが失敗し始める

会社が復元できないように、バックアップが消されるか暗号化される。暗号化より前の、同じ数時間のうちに起きる。

<Signs lang="ja" step={5} time="暗号化の前">
  <ul>
    <li><span class="where">バックアップ</span>バックアップのジョブが失敗する。またはバックアップサーバが応答しなくなる。</li>
    <li><span class="where">バックアップ</span>夜間に誰かがバックアップの管理画面にログインしている。</li>
    <li><span class="where">サーバ</span>Windows が各サーバに残している復元ポイント（シャドウコピー）が消えている。</li>
  </ul>
</Signs>

### 手順6：1つのアカウントが何もかも読む

データの持ち出しは、多くの場合、攻撃が始まって数日後に行われる。公開するという脅しが届くころには、データはとうに外にある。

<Signs lang="ja" step={6} time="中央値で約3日">
  <ul>
    <li><span class="where">ファイルサーバ</span>1つのアカウントが短時間に数千のファイルを読んでいる。</li>
    <li><span class="where">サーバ</span>サーバ上に大きな圧縮ファイルが現れる。</li>
    <li><span class="where">ファイアウォール</span>外向きの通信量が平常を大きく超えている。行き先はクラウドストレージであることが多い。</li>
  </ul>
  <SourceLine lang="ja" ids={["sophos-aar-2025", "sophos-aar-2026", "cisa-aa24-109a"]} />
</Signs>

Sophos によると、攻撃の開始からデータ持ち出しまでの時間は中央値で、2024年が72.98時間、2025年が78.83時間だった。CISA は「2時間あまり」で持ち出した Akira の事例を報告している。Sophos の2024年のデータでは、攻撃が検知されたのは持ち出しから中央値で2.7時間後であり、気づいたときにはたいていデータが出た後だった。

### 手順7：すべてのファイルの名前が一斉に変わる

暗号化は、ログを読まなくても誰もが気づく最初の手順である。

<Signs lang="ja" step={7} time="4時間未満、早ければ55分">
  <ul>
    <li><span class="where">ファイルサーバ</span>数千のファイルが数分のうちに新しい拡張子に変わる。大阪の事例では <code>.elbie</code> だった。</li>
    <li><span class="where">プリンター</span>すべてのプリンターから身代金要求文書が出てくる。半田病院では未明にこれが起きた。</li>
    <li><span class="where">サーバ</span>サーバや仮想マシンが止まる。</li>
  </ul>
  <SourceLine lang="ja" ids={["arcticwolf-akira-2025", "osaka-report-2023", "handa-report-main"]} />
</Signs>

## <Scale s="1:100" /> 速い例では、侵入から暗号化まで一晩に収まる

測定された事例のうち速いものでは、VPN へのログインから暗号化までが数時間で終わる。データ持ち出しの中央値は数日である。図 2-2 は三つの出典を一本の時間軸に並べたものである。起点は出典ごとに違い、それぞれ名前の横に書いた。最初の4時間は実寸で描き、軸の切れ目より後は4時間から4日を縮めて、Sophos の遅いほうの中央値も収めている。

<Timeline lang="ja" n="2-2" caption="侵入から各段階までの時間（三つの出典）" />

SonicWall の VPN を狙った Akira の攻撃では、ほぼすべての侵入で VPN へのログインから4時間未満で暗号化が始まり、短い例では55分だった。半田病院では、記録に残る最初のリモートデスクトップ操作が土曜日の23時57分、身代金要求文書が開かれたのが3時04分である。平日だけの監視体制も、月に一度のパッチ適用も、この速さには追いつかない。

## <Scale s="1:5" /> 経路を ATT&CK の技術に置き換え、それぞれを示すログを添える

図 2-5 は経路を [MITRE ATT&CK](https://attack.mitre.org/techniques/enterprise/) の技術に対応させ、それぞれを記録するログやテレメトリを並べたものである。イベント ID は Windows の Security ログについて Microsoft の解説ページへリンクした。Sysmon、Defender、System ログの ID はリンクなしで記した。Security ログのイベントの多くは、対応する監査ポリシーを有効にしていなければ記録されない。機器側のログも、更新の前に機器の外へ出しておかなければ役に立たない。

<AttackTable lang="ja" n="2-5" caption="侵入経路と ATT&CK の技術、それを示すテレメトリ" />

この表は防御側から見えるものを書いたもので、技術の実行方法は扱わない。手順2の背後にある機器側の欠陥は第3章で取り上げる。文書化された例として LockBit 3.0 はボリュームシャドウコピーを削除し、Windows のイベントログを消去する。手順4と5のログを、書かれた時点で各機器の外へ送っておく必要があるのはこのためである。
