<Summary lang="en">
  <p>Before anyone logs in, the appliance already handles their connection: TLS, the web request, the login page, the files it loads, SAML messages. Anyone on the internet can send it that traffic. A flaw in this code needs no password, and MFA never sees the request.</p>
  <p>The decision it implies: know which of your addresses show this surface to the internet, and turn off every part of it you do not use.</p>
</Summary>

## <Scale s="1:5" /> Everything before the login form answers anyone

Follow one connection down Fig. 5-2. The appliance terminates TLS, then a web daemon reads the request and hands it to a handler. On FortiOS that daemon is `sslvpnd`, the process Fortinet names in its advisory for CVE-2022-42475 ([FG-IR-22-398](https://www.fortiguard.com/psirt/FG-IR-22-398)). Everything in the shaded zone runs at this point: the login portal, the static files it loads, the VPN client download, the SAML or SSO endpoints, the clientless web mode, and on many deployments the management interface. Only below the zone does the appliance check a password, a second factor or a SAML assertion.

A pre-auth flaw sits inside that zone. The red line in the figure shows what exploitation does: the request goes from the web daemon to the operating system and on into the network without passing the authentication box. MFA settings make no difference to it. Of the {TOTAL} KEV-listed VPN and remote-access CVEs in the [door schedule](../../the-doors/), {PREAUTH} are reachable before login. The other {TOTAL - PREAUTH} were exploited in the wild chained behind one that is.

## <Scale s="1:5" /> This code runs before the appliance knows who is asking

Pre-auth code has to accept input from anyone, so it cannot rely on account limits or on who the sender is. In most SSL-VPN products the same web stack serves the login page and the logged-in portal. A bug anywhere in that request path is reachable from the internet.

Fig. 5-3 groups the {TOTAL} CVEs by bug class. Memory corruption is the largest group: buffer overflows, out-of-bounds reads and writes, one use-after-free. These bugs occur in code written in memory-unsafe languages such as C and C++. CISA and the FBI list CVE-2025-0282 (Ivanti Connect Secure) and CVE-2023-6549 (Citrix NetScaler) as buffer-overflow examples and say: "Threat actors frequently exploit these vulnerabilities to gain initial access to an organization's network and then move laterally to the wider network." The alert adds that the class "can be addressed by using memory safe languages". That much of this code is old C inside one large web daemon is this site's inference from the bug classes and from product lineages such as Pulse Secure to Ivanti; vendors do not publish it.

## <Scale s="1:5" /> Inventory the exposure from outside, on your own addresses

Start from what you own, then check what the internet sees. Every method below looks only at addresses and names that belong to you. Do not scan or probe addresses you do not control, and get written permission before scanning a range a provider or vendor operates for you.

<div class="table-scroll" tabindex="0">

| Method | What it tells you | What it misses |
| --- | --- | --- |
| Asset register and contracts | Every internet-facing device, including boxes a vendor installed for remote maintenance. The Osaka intrusion came in through a catering vendor's appliance (p.45). | Devices nobody recorded |
| A scan of your own public IP ranges, by you or a contracted tester | Which ports answer, and which product and version the portal or TLS certificate reveals | Addresses outside the ranges you listed |
| Exposure search engines (Shodan, Censys) queried for your own ranges and domains | What outside scanners have already indexed about you, with history | Anything they have not crawled yet |
| Certificate transparency logs for your domains | Host names such as `vpn.example[.]com` that someone set up and forgot | Devices that use only an IP address |
| Vendor support portal | Model, serial number and the date support ends | Devices registered to a former contractor |

</div>

## <Scale s="1:5" /> Turn off what does not need to answer

Fig. 5-4 is the same appliance after the surface is cut down. Each change removes a part of the shaded zone from the internet's reach. None of them fixes a vulnerable handler that stays enabled, so patching still applies.

<Fig lang="en" n="5-4" caption="The same appliance with the management UI off the internet, unused modes disabled and a source-IP allow-list in front" sources={["ch5-cccs-itsm80101", "handa-report-tech", "ch5-jpcert-at-2024-0004"]} nts>
  <PreauthLifecycle lang="en" variant="reduced" label="The same appliance as Fig. 5-2. A green bar marks a source-IP allow-list in front of the appliance. Clientless mode is crossed out as disabled and the management UI is crossed out as moved off the internet. No red route." />
</Fig>

<div class="table-scroll" tabindex="0">

| Change | What leaves the pre-auth zone | Basis |
| --- | --- | --- |
| Move the management interface to a separate management network | The administrative web UI and its API | CCCS: NMIs "should not be directly exposed to the Internet." |
| Allow the portal only from known source addresses, where users connect from fixed sites | Every handler, for everyone outside the list | Handa had no source restriction, so "インターネット上のすべてのシステムからの接続が可能であった。" (technical volume, printed p.11). Mobile workers rarely have fixed addresses, so this fits partner and site-to-site access best. |
| Disable features you do not use: clientless web mode, unused SSO integrations, legacy protocol versions | The code behind those features | CCCS: "Deactivate any functionality that is not required." CVE-2026-24858 affected only devices with FortiCloud SSO enabled. |
| As a stopgap during an unpatched KEV, disable the SSL-VPN function | The whole portal | JPCERT/CC on CVE-2024-21762: "SSL VPN機能を無効にすることで本脆弱性の回避が可能です。" |

</div>
